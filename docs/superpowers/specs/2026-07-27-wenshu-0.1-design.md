# 文枢 0.1 设计规格

## 1. 目标

文枢 0.1 是面向中文内容工作的本地 AI 工作台。首个可交付闭环是：用户在会话中上传资料、粘贴文字或链接，文枢整理并撰写文章，使用内置 Python 内容能力生成封面与正文配图，在本地预览后，经用户明确批准，将文章保存到微信公众号草稿箱。

成功标准：

1. Linux 浏览器开发版可以完成全流程。
2. 用户通过文枢界面配置一个微信公众号的 AppID 和 AppSecret。
3. 文枢内容助手能够从聊天资料生成带 Frontmatter 的 Markdown 文章、封面和正文配图。
4. 用户能够看到公众号最终 HTML、标题、摘要、封面和图片数量。
5. 未经用户批准，不调用公众号写接口。
6. 批准后，真实公众号后台出现对应草稿，并由文枢保存包含 media_id 的本地回执。
7. AppSecret 和 access token 不进入模型上下文、会话内容、普通日志或审计参数。
8. 内容生成、图片生成和公众号草稿全部由文枢第一方 Python Modules、Tools 和 Connectors 实现，不依赖 Bun、外部脚本或第三方 Skill 包。

## 2. 首版范围

### 2.1 包含

- 用户可见品牌改为“文枢 WenShu”。
- 首页、会话、模型配置、内置内容能力、公众号连接、预览、审批和错误提示等核心路径中文化。
- 新增默认 Persona“文枢内容助手”。
- 保留当前 OpenAI 默认聊天模型；其他现有模型继续可选。
- 新增第一方 Python 文章格式、封面规划、正文配图规划和图片生成 Modules。
- 新增第一方 Python OpenAI Images Adapter，默认图片模型为 `gpt-image-2`。
- 新增第一方 Python 微信公众号配置、HTML 渲染、素材上传、预览和创建草稿能力。
- 默认隐藏 Slack、HubSpot、Jira 等非核心国外连接器，但保留其代码和测试。
- 默认关闭并隐藏 OpenWorker Cloud 登录、Gallery、托管 OAuth 和 Relay。
- 移除文枢构建中的 OpenWorker 上游自动更新端点。

### 2.2 不包含

- 微信公众号正式发布。
- 多公众号账号管理。
- 文章选题、版本、标签和发布状态等独立 CMS。
- 全界面一次性中文化。
- 删除国外连接器实现。
- 重命名 Python 包 coworker、.coworker 配置目录、COWORKER_* 环境变量、数据库文件或浏览器本地存储键。
- 自建文枢云服务、OAuth Broker、Relay 或更新服务。
- Bun、TypeScript 内容脚本、外部 Skill 包或第三方运行时代码。
- 浏览器自动操作公众号后台或 SSH 远程发布。
- OpenAI Images 以外的图片生成 Adapter。

## 3. 总体架构

现有分层保持不变，内容能力作为第一方 Python Modules 接入既有工具注册、权限和连接器体系：

```text
文枢 React/Tauri 桌面端
        ↓
本地 FastAPI / WebSocket
        ↓
文枢内容 Persona + ToolRegistry + 权限审批
        ↓
Content Modules ── ImageGenerationProvider
        ↓                    ↓
WeChat Connector      OpenAI Images Adapter
        ↓
微信公众号 API
```

职责划分：

- 文枢内容助手负责理解资料、规划文章、封面和配图，并编排第一方 Tools 形成交付物。
- Content Modules 负责文章模型、Frontmatter、Markdown 规范化、封面和配图请求模型。
- ImageGenerationProvider 定义统一图片请求和结果 Interface；OpenAI Images Adapter 是 0.1 的首个实现。
- WeChat Connector 负责公众号账号配置、SecretStore、Markdown 到公众号 HTML、素材上传、草稿创建、错误映射、审批元数据、审计脱敏和本地回执。
- 桌面端负责中文配置、预览和批准交互。
- SkillLoader 继续服务用户可安装 Skills，但文枢 0.1 内容闭环不依赖任何外部 Skill。

## 4. 产品配置

新增集中的产品配置 Module，向后端调用方提供小型 Interface：

- 产品名称与显示名称。
- 默认 Persona。
- 默认可见连接器集合。
- Cloud、Gallery、托管 OAuth、Relay 是否启用。
- 内置内容能力和 Provider 开关集合。

前端从后端设置或健康信息获取运行时产品元数据。Tauri 的 productName、identifier、publisher、图标和更新器属于构建期元数据，仍在 Tauri 配置中明确设置，不引入跨语言动态配置机制。

文枢默认配置：

- 名称：文枢 WenShu。
- 默认 Persona：文枢内容助手。
- 默认模型：保留当前 OpenAI 默认。
- 国外连接器：代码保留、界面隐藏。
- OpenWorker Cloud 相关能力：关闭。
- 上游更新器：关闭。

## 5. 文枢内容助手

文枢内容助手复用现有 knowledge-family Agent 能力：文件、搜索、Shell、Todo、用户 Skills、记忆、审批和会话工作区。文章、图片和公众号能力作为该 Persona 的第一方 Tools 直接注册，用户无需安装 Skill。

其系统提示明确以下流程：

1. 读取用户在聊天中上传或提供的资料。
2. 确认文章目的、受众和必要约束；已有信息充分时不重复询问。
3. 生成结构清晰、带规范 Frontmatter 的 Markdown 正文。
4. 根据文章主题生成 CoverRequest，包括类型、色彩、渲染风格、文字密度、情绪和宽高比。
5. 分析文章结构，生成 IllustrationPlan；只在确有信息或表达价值的位置安排配图，并保持全文风格一致。
6. 调用 Python 图片生成 Tool，将 OpenAI Images 结果保存到文章目录。
7. 调用公众号预览 Tool 生成最终 HTML。
8. 展示预览并等待用户明确批准。
9. 只在批准后创建公众号草稿。

默认封面偏好：

- 类型：conceptual。
- 配色：cool。
- 渲染：digital。
- 文字：title-only。
- 情绪：bold。
- 比例：2.35:1。
- 提示词语言：中文。

## 6. 第一方内容与图片 Modules

### 6.1 Content Modules

新增 `coworker/content/`，集中实现内容领域模型和确定性转换：

```text
coworker/content/
├── models.py
├── frontmatter.py
├── markdown.py
├── cover.py
├── illustrations.py
└── tools.py
```

核心模型：

- `ArticleDocument`：标题、作者、摘要、原文链接、Markdown 正文和本地资产。
- `CoverRequest`：封面类型、配色、渲染风格、文字密度、情绪、比例、提示词和输出路径。
- `IllustrationPlan`：文章位置、图片用途、提示词、风格、配色、比例和输出路径列表。
- `ImageAsset`：本地路径、媒体类型、尺寸、内容哈希和生成元数据。

模型负责验证和规范化；需要判断和创意的规划由内容 Persona 完成，不把第二个隐藏 LLM Agent 塞进 Python Implementation。

### 6.2 图片生成 Interface

新增 `coworker/image_generation/`：

```text
coworker/image_generation/
├── base.py
├── models.py
├── registry.py
├── openai_images.py
└── tools.py
```

统一 Interface：

```python
class ImageGenerationProvider:
    async def generate(self, request: ImageRequest) -> ImageResult:
        ...
```

`ImageRequest` 包含提示词、可选参考图、宽高比、质量、输出路径和数量。`ImageResult` 包含落盘后的图片资产和非敏感提供商元数据。

0.1 仅实现 OpenAI Images Adapter：

- 复用现有 OpenAI Provider Profile 中的 API key 和自定义 endpoint。
- 图片模型设置独立于聊天模型，默认 `gpt-image-2`。
- 不把 API key 传入 Agent 参数或提示词。
- 生成结果必须下载并写入当前会话允许目录。
- 外部调用失败、响应缺图、图片损坏或写入失败时返回结构化错误。
- 图片生成属于可能产生费用的外部操作，调用前使用现有审批机制。

### 6.3 内置能力 Interface

内容 Persona 直接获得以下第一方 Tools：

```text
generate_content_image(request)
prepare_wechat_draft(article_path, theme, color?, cover_path?)
create_wechat_draft(article_path, theme, color?, cover_path?)
```

封面和配图规划属于 Persona 的内置工作流；`generate_content_image` 只执行经过模型验证的 ImageRequest。该能力与用户可安装 Skills 并存，但不要求 SkillLoader、脚本运行时或额外安装步骤。

## 7. 内容交付格式

每篇文章在会话工作区形成：

```text
articles/<slug>/
├── article.md
├── cover.png
├── images/
├── article.html
└── receipt.json
```

- `article.md` 是内容生产和公众号 Connector 之间的主要 Interface。
- `cover.png` 和 `images/` 由第一方 Python 图片生成 Tool 生成或由用户提供。
- `article.html` 由第一方 Python WeChat Renderer 生成，用于最终预览和草稿提交。
- `receipt.json` 只在成功创建草稿后由文枢写入。

Markdown Frontmatter 承载公众号元数据：

```yaml
---
title: 文枢项目介绍
author: 作者
summary: 面向中文内容工作场景的本地 AI Worker
coverImage: cover.png
sourceUrl: https://example.com
---
```

字段约束由文枢内容模型和微信公众号接口共同定义：标题必填；封面必填或由正文首图回退；摘要、作者和原文链接可选；评论选项来自账号设置。

## 8. WeChat Connector

### 8.1 Python Module

新增第一方 Python Connector：

```text
coworker/connectors/wechat/
├── client.py
├── models.py
├── credentials.py
├── renderer.py
├── images.py
├── drafts.py
├── errors.py
└── tools.py
```

- `client.py` 封装 `httpx`、access token 缓存、超时和公众号错误响应。
- `renderer.py` 将 Markdown 转换为带内联样式的公众号兼容 HTML，处理主题、主色、代码、列表、引用和外链底部引用。
- `images.py` 校验并处理本地图片，上传正文图片取得远端 URL，上传封面永久素材取得 `thumb_media_id`。
- `drafts.py` 组装并调用 `draft/add`。
- `tools.py` 将预览和创建草稿注册到现有 Connector ToolRegistry。

### 8.2 对 Agent 的 Interface

首版暴露两个工具：

```text
prepare_wechat_draft(article_path, theme, color?, cover_path?)
create_wechat_draft(article_path, theme, color?, cover_path?)
```

`prepare_wechat_draft`：

- 读取当前会话允许目录内的 Markdown 和图片。
- 解析并校验 Frontmatter。
- 使用 Python Renderer 生成 `article.html`。
- 返回标题、作者、摘要、封面、图片数量、主题和预览文件路径。
- 不请求公众号 access token，不执行外部写操作。

`create_wechat_draft`：

- 是需要批准的外部写工具。
- 校验输入内容哈希仍与已展示的预览一致。
- 从 SecretStore 读取 AppID/AppSecret。
- 使用 Python Client 获取或复用 access token。
- 上传正文图片和封面后调用 `draft/add`。
- 成功后保存回执并返回 media_id。

### 8.3 凭据和账号

首版只支持一个公众号账号。连接页面收集 AppID 和 AppSecret，并写入现有 SecretStore。连接检查通过公众号 token 接口验证凭据和接口可达性；错误按凭据无效、IP 白名单、权限不足、限流和网络故障分类显示。

凭据不得写入：

- 模型消息。
- Markdown Frontmatter。
- 会话数据库正文。
- Todo 或审批说明。
- 普通应用日志。
- 审计工具参数。

### 8.4 审批

调用 `create_wechat_draft` 前使用现有 Approval Card。卡片显示：

- 公众号连接名称。
- 文章标题。
- 摘要。
- 封面缩略信息。
- 正文图片数量。
- 主题和颜色。
- 操作说明“保存到公众号草稿箱，不会正式发布”。

首版不注册正式发布工具，因此 Persona 无法通过 Connector 绕过草稿箱。

### 8.5 重复提交

成功回执包含：

- 规范化 Markdown、图片和提交选项的内容哈希。
- media_id。
- 标题。
- 提交时间。
- 非敏感账号标识。

当相同内容哈希再次提交时，Connector 返回已有成功回执，不创建重复草稿。文章正文、图片或提交选项发生变化后产生新哈希，可创建新草稿。

## 9. 数据流

```text
用户上传资料或粘贴内容
        ↓
文枢内容助手整理、撰写 article.md
        ↓
Persona 生成 CoverRequest 和 IllustrationPlan
        ↓
Python OpenAI Images Adapter 生成 cover.png 与 images/
        ↓
prepare_wechat_draft 使用 Python Renderer 生成 article.html
        ↓
桌面端展示标题、摘要、HTML、封面、图片数量
        ↓
用户批准“保存到公众号草稿箱”
        ↓
create_wechat_draft 从 SecretStore 读取凭据
        ↓
Python WeChat Connector 上传正文图片和封面，调用 draft/add
        ↓
文枢保存 receipt.json，显示 media_id 和公众号后台入口
```

## 10. 错误和部分失败

图片生成前校验：

- 输出路径位于当前允许目录。
- 提示词非空且长度受限。
- 参考图存在、类型和大小受支持。
- 请求的宽高比和质量受 OpenAI Images Adapter 支持。

公众号提交前校验：

- 路径位于当前允许目录。
- Markdown 文件存在且可读取。
- 标题可解析。
- 封面存在或正文存在可用首图。
- 图片格式和大小可被 Python 图片处理 Module 支持。
- 本地预览成功且提交内容哈希与预览一致。

提交过程中：

1. 任一正文图片上传失败则停止，不调用 `draft/add`。
2. 封面上传失败则停止，不调用 `draft/add`。
3. `draft/add` 失败则报告错误码和中文操作建议。
4. 已上传到素材库但公众号接口不支持回滚的图片必须在结果中说明，不宣称撤销成功。
5. 网络结果不明确时不自动盲重试 `draft/add`；返回“提交结果未知”，要求用户先检查草稿箱。
6. 公众号响应缺少 `media_id` 时不能凭 HTTP 成功状态猜测草稿成功。

## 12. 原项目功能处理

- Slack、HubSpot、Jira 等国外连接器由产品配置默认隐藏，源码和现有测试保留。
- OpenWorker Cloud 登录入口隐藏，Cloud 客户端不在文枢默认运行路径启动。
- Gallery、托管 OAuth 和 Relay 随 Cloud 配置关闭。
- Tauri updater 不指向 OpenWorker 下载地址或公钥；0.1 开发版关闭自动更新。
- README 和运行说明改为文枢，并保留 OpenWorker 与 MIT 许可归属。
- 内部 coworker 标识首版不迁移，以维持数据和上游兼容。

## 13. 验证策略

### 13.1 后端单元测试

- 产品配置默认值和连接器可见性。
- ArticleDocument、CoverRequest、IllustrationPlan 和 ImageAsset 的验证。
- OpenAI Images 请求构造、凭据解析、图片下载、损坏响应和目录限制。
- 公众号凭据保存、access token 缓存和脱敏。
- Markdown Frontmatter 解析和规范化。
- 公众号 HTML 的主题、主色、外链引用和本地图片定位。
- 正文图片 URL 替换与封面 `thumb_media_id`。
- `article_path` 与 `cover_path` 的目录限制。
- 预览内容哈希和提交前一致性检查。
- 微信错误码映射。
- 内容哈希和重复提交回执。
- 现有国外连接器在隐藏后仍可由非文枢配置加载。

### 13.2 HTTP Adapter 合约测试

使用 `httpx` 假传输，不请求真实 OpenAI 或公众号：

- OpenAI Images 成功返回 URL 或图片数据并正确落盘。
- 图片生成收费操作需要审批。
- 公众号 access token 成功、过期刷新和错误响应。
- 正文图片先于封面和 `draft/add` 上传。
- `draft/add` 成功响应解析为 media_id。
- 非 2xx、业务 errcode、超时和不完整响应正确映射。
- API key、AppSecret 和 access token 不出现在 Tool 参数、日志和审计记录。

### 13.3 前端测试

- 文枢品牌和核心中文文案。
- 国外连接器默认隐藏。
- OpenAI Images 模型设置和连接状态。
- 公众号 AppID/AppSecret 表单与连接状态。
- 公众号预览展示。
- Approval Card 明确说明只创建草稿。
- 成功、重复、失败和结果未知状态。

### 13.4 烟雾验证

1. 在 Linux 启动本地后端和浏览器 UI。
2. 在界面中配置 OpenAI API key 和真实公众号 AppID/AppSecret。
3. 上传一组测试资料。
4. 生成测试文章、封面和至少一张正文配图。
5. 打开公众号最终 HTML 预览。
6. 批准创建草稿。
7. 在公众号后台确认草稿存在，标题、正文、图片和封面正确。
8. 确认本地 `receipt.json` 的 media_id 与结果一致。
9. 再次提交相同内容，确认不产生第二份草稿。

真实凭据不得进入自动化测试仓库。

## 14. 实施顺序约束

后续实施计划应按以下依赖顺序拆分：

1. 文枢产品配置和原云/更新路径关闭。
2. 可见品牌、默认 Persona 和核心中文路径。
3. Content Models 和第一方内容 Tools。
4. ImageGenerationProvider Interface 与 Python OpenAI Images Adapter。
5. 公众号凭据、Python Client 和连接页面。
6. Python Markdown Renderer 与本地预览。
7. 审批后的素材上传、草稿创建、回执和重复提交防护。
8. 前后端自动化验证。
9. 真实 OpenAI Images 与公众号烟雾验证。

任何阶段都不得添加正式发布工具。
